Section 01

What Is Pagination & Why It Exists

Pagination is the practice of breaking a large dataset into smaller, sequential chunks (pages) that are delivered and rendered incrementally. It is one of the most fundamental problems in systems design because nearly every production system eventually handles datasets too large to return in a single response.

Core Problems Pagination Solves

Memory Pressure
  • DB can't hold millions of rows in RAM for sorting
  • Application server would OOM serialising large JSON
  • Client browser would freeze rendering 100k rows
Latency
  • Full table scans take seconds for large tables
  • Network transfer of large payloads is slow
  • Time-to-first-byte (TTFB) suffers without chunking
Cost
  • Unnecessary rows read = wasted DB I/O
  • Bandwidth charges per GB transferred
  • Compute cost for serialising unused data
Consistency
  • Underlying data changes between page fetches
  • "Phantom rows" appearing or disappearing
  • Duplicate entries at page boundaries

Fundamental Concepts

Page Size (limit): Number of records per page. Chosen based on UX needs vs. backend cost. Typical values: 10–25 for UI, 100–1000 for API consumers, up to 10,000 for ETL/export.

Page Identifier: How the system knows which page to return. This is the key differentiator between pagination strategies — it is either a positional (OFFSET) or a relational (cursor/key) identifier.

Total Count: Not always necessary and often expensive. Many modern APIs omit it. When present, enables progress indicators. When absent, requires "load more" UX patterns.

Stable Ordering: All pagination strategies require a deterministic, stable sort. Without it, the same query run twice can return different orderings, causing rows to be skipped or duplicated across pages.

The Pagination Trilemma
You generally cannot have all three simultaneously: arbitrary navigation (jump to page N), consistency (no duplicates/skips), and performance at scale. Every strategy makes a different trade-off among these three.
Section 02

Offset / Page-Based Pagination

The most intuitive and widely implemented strategy. The client specifies how many rows to skip (OFFSET) and how many to return (LIMIT).

SQL Implementation

-- Page 1 (rows 1–20)
SELECT * FROM orders
ORDER BY created_at DESC
LIMIT 20 OFFSET 0;

-- Page 3 (rows 41–60)
SELECT * FROM orders
ORDER BY created_at DESC
LIMIT 20 OFFSET 40;

-- Total count (for progress bar)
SELECT COUNT(*) FROM orders; -- EXPENSIVE on large tables
OFFSET = (page_number - 1) × page_size

REST API Design

# Request
GET /api/orders?page=3&page_size=20

# Response
{
  "data": [...],
  "pagination": {
    "page": 3,
    "page_size": 20,
    "total_count": 1847,
    "total_pages": 93,
    "has_next": true,
    "has_prev": true
  }
}

How the Database Actually Executes OFFSET

This is the critical insight most engineers miss. The database does not skip rows cheaply. It must:

  1. Read ALL rows matching the WHERE clause
  2. Sort them (if not covered by an index)
  3. Discard the first OFFSET rows
  4. Return the next LIMIT rows
The Deep Pagination Problem
OFFSET 1000000 LIMIT 20 forces the DB to read and discard 1 million rows before returning your 20. At large offsets, this is catastrophically slow — O(OFFSET) time complexity. This is called the late row lookup problem or deep pagination problem.

The "Deferred Join" / Index Scan Optimisation

Use a subquery or CTE to first get only the primary keys via the index, then join back to fetch full row data. This is significantly faster because it avoids fetching wide rows during the offset phase:

-- SLOW: Fetches full row data for all OFFSET rows
SELECT * FROM orders ORDER BY id LIMIT 20 OFFSET 100000;

-- FAST: Index-only scan for offset, then narrow join
SELECT o.* FROM orders o
INNER JOIN (
  SELECT id FROM orders ORDER BY id LIMIT 20 OFFSET 100000
) ids ON o.id = ids.id;

Consistency Problem: The Shifting Dataset

When records are inserted or deleted between page fetches, offset-based pagination produces incorrect results:

Scenario: User views page 1 (rows 1–10). A new record is inserted. User requests page 2 (rows 11–20). The old row 10 is now row 11 — it appears again. This is called a phantom read.

Summary

DimensionAssessment
Arbitrary navigation (jump to page N)✓ Excellent
Performance on small datasets (<100k rows)✓ Good
Performance on large offsets✗ Poor — O(n) scan
Consistency during mutations✗ Poor — phantom reads

Best suited for: Admin panels, content management, low-write datasets, internal tools, any use case requiring "jump to page N" where data mutates slowly.

Section 03

Cursor / Keyset Pagination

Instead of telling the database how many rows to skip, cursor pagination tells it where to continue from. The cursor is a pointer into the dataset — typically an encoded value of the last record seen.

Core Mechanism

A cursor encodes the sort key(s) of the last item returned. On the next request, a WHERE clause replaces the OFFSET, allowing the DB to seek directly to the right position using an index.

-- First page (no cursor)
SELECT id, created_at, title FROM posts
ORDER BY created_at DESC, id DESC
LIMIT 20;

-- Subsequent page: last item had created_at='2024-01-15 10:30:00', id=4892
SELECT id, created_at, title FROM posts
WHERE (created_at, id) < ('2024-01-15 10:30:00', 4892)
ORDER BY created_at DESC, id DESC
LIMIT 20;
Row Value Comparison
The (col1, col2) < (val1, val2) syntax (tuple comparison / row value comparison) is supported in PostgreSQL and MySQL. It correctly handles the composite seek: it means "col1 < val1, OR (col1 = val1 AND col2 < val2)". This is essential when the sort key is not unique.

Why It's Faster: Index Seek vs Index Scan

With an index on (created_at DESC, id DESC), the WHERE (created_at, id) < (...) clause does a B-tree seek — O(log N) — directly to the right position, then scans forward for LIMIT rows. No rows are discarded. Compare this to OFFSET which always scans and discards.

Cursor Encoding

Cursors should be opaque to clients — they should not be interpretable or manually constructable. Common approaches:

// Option 1: Base64 encode the sort key(s)
const cursor = btoa(JSON.stringify({
  created_at: "2024-01-15T10:30:00Z",
  id: 4892
}));
// → "eyJjcmVhdGVkX2F0IjoiMjAyNC0wMS0xNVQxMDozMDowMFoiLCJpZCI6NDg5Mn0="

// Option 2: Encrypt cursor (prevents cursor injection attacks)
const cursor = encrypt(JSON.stringify({created_at, id}), SECRET_KEY);

// Option 3: Server-side cursor storage (Redis)
const cursorId = uuidv4();
await redis.setex(`cursor:${cursorId}`, 3600, JSON.stringify({created_at, id}));
// Returns cursorId to client; server looks up actual values

Handling Non-Unique Sort Keys

If ORDER BY created_at and multiple rows share the same timestamp, the cursor is ambiguous. Always add a unique tiebreaker (usually id) to the sort key. This is the most common cursor pagination bug.

Bi-directional Cursors

For "previous page" support, you need both a before and after cursor. This requires reversing the sort order for the previous-page query:

-- Previous page: reverse sort, then re-reverse in application
SELECT * FROM posts
WHERE (created_at, id) > (:cursor_created_at, :cursor_id)
ORDER BY created_at ASC, id ASC  -- reversed
LIMIT 20;
-- Then reverse the result set in application code

REST API Design

GET /api/posts?limit=20&after=eyJjcmVhdGVkX2F0IjoiMjAyN...

{
  "data": [...],
  "pagination": {
    "next_cursor": "eyJjcmVhdGVkX2F0IjoiMjAyNC0wMS0xMyIsImlkIjo0ODcyfQ==",
    "prev_cursor": "eyJjcmVhdGVkX2F0IjoiMjAyNC0wMS0xNSIsImlkIjo0ODkyfQ==",
    "has_next": true,
    "has_prev": true
    // NOTE: no total_count — impossible to compute efficiently
  }
}

Section 04

Seek Method & Bookmark Pagination

The Seek Method (coined by Markus Winand) is essentially keyset pagination made explicit — it uses WHERE conditions to "seek" past already-seen records. Bookmark pagination is a variant where the server stores the cursor server-side and returns an opaque bookmark token.

Seek Method in Detail

-- Multi-column seek with mixed sort directions
-- ORDER BY last_name ASC, first_name ASC, id ASC

SELECT * FROM users
WHERE
  last_name > :last_name
  OR (last_name = :last_name AND first_name > :first_name)
  OR (last_name = :last_name AND first_name = :first_name AND id > :id)
ORDER BY last_name ASC, first_name ASC, id ASC
LIMIT 20;

This explicit OR expansion is equivalent to row value comparison but works in all databases including those that don't support tuple comparison (SQLite, some older MySQL versions).

Server-Side Bookmark Storage

Instead of encoding cursor data in the token, store it server-side in Redis and return an opaque UUID. This prevents clients from reverse-engineering or forging cursors, and allows cursors to carry arbitrary metadata:

// Server: create bookmark
async function createBookmark(lastRow, userId, queryParams) {
  const bookmarkId = uuidv4();
  await redis.setex(
    `bookmark:${userId}:${bookmarkId}`,
    86400,  // 24h TTL
    JSON.stringify({ lastRow, queryParams, createdAt: Date.now() })
  );
  return bookmarkId;
}

// Server: resolve bookmark
async function resolveBookmark(bookmarkId, userId) {
  const data = await redis.get(`bookmark:${userId}:${bookmarkId}`);
  if (!data) throw new Error('Cursor expired or invalid');
  return JSON.parse(data);
}
When to Use Server-Side Cursors
Server-side cursors are preferable when: (1) cursor data is large, (2) you need cursor expiry/revocation, (3) security is critical and you don't want clients to see pagination internals, (4) you want to prevent cursor replay attacks.
Section 05

Time-Based Pagination

Time-based pagination uses timestamp ranges instead of offsets or cursors. It's a natural fit for time-series data, feeds, logs, and audit trails.

Fixed Time Windows

-- Fetch events in a specific hour
SELECT * FROM events
WHERE occurred_at >= '2024-01-15 10:00:00'
  AND occurred_at < '2024-01-15 11:00:00'
ORDER BY occurred_at ASC
LIMIT 1000;

Sliding Time Windows (Feed Pattern)

GET /api/feed?before=2024-01-15T10:30:00Z&limit=20
GET /api/feed?after=2024-01-15T10:30:00Z&limit=20

-- "Load newer" (pull-to-refresh)
SELECT * FROM posts
WHERE created_at > :since_timestamp
ORDER BY created_at ASC
LIMIT 50;

-- "Load older" (infinite scroll downward)
SELECT * FROM posts
WHERE created_at < :before_timestamp
ORDER BY created_at DESC
LIMIT 20;

The Timestamp Tie Problem

Multiple events can share the same timestamp (especially at millisecond or even microsecond resolution under high write load). Always combine timestamp with a unique ID as a tiebreaker. Alternatively, use a monotonic sequence (Snowflake ID, ULID) that encodes time in the ID itself:

Snowflake ID
  • 41 bits timestamp (ms precision)
  • 10 bits machine/datacenter ID
  • 12 bits sequence number
  • Globally sortable by time, unique
  • Used by: Twitter, Discord
ULID
  • 48 bits timestamp
  • 80 bits random
  • Lexicographically sortable
  • URL-safe (Crockford Base32)
  • Drop-in UUID replacement
UUID v7
  • 48 bits Unix timestamp (ms)
  • 74 bits random
  • Monotonically increasing
  • RFC-standard format
  • Native DB support emerging
Section 06

Hybrid & Composite Strategies

Offset + Cursor Hybrid

Use offset pagination for the first N pages (fast, enables page jumping) and automatically switch to cursor pagination for deep pages. This is used by Google Search — you can jump to pages 1–10 easily, but can't jump to page 10,000.

function paginate(page, pageSize) {
  const DEEP_PAGE_THRESHOLD = 100;
  if (page <= DEEP_PAGE_THRESHOLD) {
    return offsetPaginate(page, pageSize);
  }
  // For deep pages, use a pre-computed cursor at a checkpoint
  const checkpoint = getCheckpointCursor(DEEP_PAGE_THRESHOLD, pageSize);
  const remainingOffset = (page - DEEP_PAGE_THRESHOLD - 1) * pageSize;
  return cursorPaginateFromCheckpoint(checkpoint, remainingOffset);
}

Keyset + Total Count

Run the COUNT query asynchronously or use an approximation (PostgreSQL's pg_class.reltuples) to provide a progress indicator alongside cursor pagination:

-- PostgreSQL approximate count (near-instant)
SELECT reltuples::bigint AS approx_count
FROM pg_class
WHERE relname = 'orders';

-- Or with filtered WHERE clause: use EXPLAIN to get estimate
EXPLAIN SELECT * FROM orders WHERE status = 'pending';
-- Parse "rows=XXXX" from output

Snapshot Pagination

For guaranteed consistency across all pages, take a snapshot of the dataset and paginate over it. Used in financial reports, exports, and audit contexts:

-- PostgreSQL: use a transaction with REPEATABLE READ isolation
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;

SELECT * FROM transactions
ORDER BY id
LIMIT 100 OFFSET :offset;

-- All subsequent queries in this transaction see the same snapshot
COMMIT;
Snapshot Limitations
Long-running snapshot transactions hold open read locks and can prevent VACUUM in PostgreSQL. For very large exports, use a materialized view, a temporary table, or an async export job instead.
Section 07

Database Internals & Indexing

Why Index Design Is Critical for Pagination

The entire performance difference between pagination strategies comes down to what the database's query planner can do with the available indexes.

B-Tree Index and Pagination

B-Tree (Balanced Tree) indexes are the default in PostgreSQL, MySQL, and most relational databases. For pagination:

  • Seeks (cursor WHERE clause) cost O(log N) — traversing tree height
  • Range scans (scanning LIMIT rows after seek) cost O(LIMIT) — sequential leaf node traversal
  • Total cost per page: O(log N + LIMIT) — independent of depth

Covering Indexes

A covering index includes all columns referenced in the query, eliminating the need for a heap lookup (table row fetch). For pagination queries, this means the DB never touches the table — only the index:

-- Query
SELECT id, title, created_at FROM posts
WHERE (created_at, id) < (:ts, :id)
ORDER BY created_at DESC, id DESC
LIMIT 20;

-- Covering index: includes all SELECT columns + WHERE/ORDER BY columns
CREATE INDEX idx_posts_pagination
  ON posts (created_at DESC, id DESC)
  INCLUDE (title);  -- PostgreSQL 11+ INCLUDE syntax

-- MySQL equivalent
CREATE INDEX idx_posts_pagination
  ON posts (created_at DESC, id, title);

Partial Indexes

For paginating over filtered datasets (e.g., WHERE status = 'active'), a partial index over only the matching rows is much smaller and faster:

CREATE INDEX idx_active_posts_cursor
  ON posts (created_at DESC, id DESC)
  WHERE status = 'active';

Index-Only Scans vs Heap Scans

PostgreSQL's visibility map allows index-only scans when all required columns are in the index and the heap blocks are all-visible. This is 2–10x faster for pagination. Keep tables well-vacuumed to keep heap blocks marked visible.

NoSQL: MongoDB

// Offset-based (slow at depth)
db.orders.find({}).sort({createdAt: -1}).skip(100).limit(20)

// Cursor-based (fast)
db.orders.find({
  createdAt: { $lt: lastCreatedAt },
  _id: { $lt: lastId }
}).sort({createdAt: -1, _id: -1}).limit(20)

// Required index
db.orders.createIndex({ createdAt: -1, _id: -1 })

NoSQL: Cassandra

Cassandra is designed around partition keys and clustering columns. Its data model inherently supports efficient range scans within a partition, making it naturally suited to cursor pagination — but only within a partition. Cross-partition pagination is expensive and discouraged.

-- Cassandra table designed for timeline pagination
CREATE TABLE user_feed (
  user_id    UUID,
  post_time  TIMESTAMP,
  post_id    UUID,
  content    TEXT,
  PRIMARY KEY (user_id, post_time, post_id)
) WITH CLUSTERING ORDER BY (post_time DESC, post_id DESC);

-- Efficient cursor pagination (within partition)
SELECT * FROM user_feed
WHERE user_id = :uid
  AND (post_time, post_id) < (:cursor_time, :cursor_id)
LIMIT 20;

NoSQL: Redis

Redis Sorted Sets (ZSET) are the ideal structure for real-time paginated feeds. Score = timestamp.

# Add items
ZADD feed:user:123 1705312200 "post:456"
ZADD feed:user:123 1705312100 "post:455"

# Offset pagination (ZRANGE with BYSCORE)
ZRANGE feed:user:123 +inf -inf BYSCORE LIMIT 0 20 REV

# Cursor pagination: fetch 20 items before score X
ZRANGEBYSCORE feed:user:123 -inf (1705312200 LIMIT 0 20

# Count total (O(1))
ZCARD feed:user:123

Idempotency & Stability

Pagination requests must be idempotent — the same request must return the same data. This is violated by offset pagination on mutable data. Consider adding a snapshot_at parameter for export use cases.

Rate Limiting Considerations

Clients that rapidly iterate all pages can be expensive. Strategies: per-page rate limits, cursor expiry (invalidate old cursors after 24h), maximum page depth limits, and requiring authentication for deep pagination.

API Versioning and Pagination

Changing the pagination strategy between API versions (e.g., offset to cursor) is a breaking change. The response shape changes, client code must update, and cursors from v1 are not valid in v2. Version clearly, provide migration guides, and support both strategies during a transition period.

GraphQL Pagination

The Relay Cursor Connections Spec

The Relay spec (developed by Facebook/Meta) is the de facto standard for GraphQL pagination. It defines a formal shape for paginated results using connections, edges, and nodes.

# GraphQL Query
query {
  orders(first: 20, after: "cursor_opaque_string") {
    pageInfo {
      hasNextPage
      hasPreviousPage
      startCursor
      endCursor
    }
    totalCount
    edges {
      cursor
      node {
        id
        amount
        status
        createdAt
      }
    }
  }
}
// Response
{
  "data": {
    "orders": {
      "pageInfo": {
        "hasNextPage": true,
        "hasPreviousPage": false,
        "startCursor": "YXJyYXljb25uZWN0aW9uOjA=",
        "endCursor": "YXJyYXljb25uZWN0aW9uOjE5"
      },
      "totalCount": 1847,
      "edges": [
        {
          "cursor": "YXJyYXljb25uZWN0aW9uOjA=",
          "node": { "id": "1", "amount": 99.99 }
        }
      ]
    }
  }
}

Relay Connection Arguments

ArgumentMeaningDirection
first: NReturn first N edges after cursorForward
after: cursorStart after this cursorForward
last: NReturn last N edges before cursorBackward
before: cursorStart before this cursorBackward
Rule: first/after and last/before must not be combined
Combining forward and backward arguments (e.g., first: 5, last: 5) is undefined behaviour in the Relay spec. Validate and reject such combinations server-side.

Simple Offset-Based GraphQL (non-Relay)

query {
  orders(limit: 20, offset: 40) {
    id
    amount
  }
}

# Or page-based
query {
  orders(page: 3, perPage: 20) {
    items { id amount }
    total
    pageCount
  }
}

Implementing Relay in Node.js

import { connectionFromArray } from 'graphql-relay';

const resolvers = {
  Query: {
    orders: async (_, { first, after, last, before }, ctx) => {
      // Decode cursor
      const afterId = after ? decodeCursor(after) : null;
      const beforeId = before ? decodeCursor(before) : null;

      // Build keyset query
      const orders = await ctx.db.orders.findMany({
        where: {
          ...(afterId && { id: { gt: afterId } }),
          ...(beforeId && { id: { lt: beforeId } }),
        },
        take: first ?? last,
        orderBy: { id: 'asc' }
      });

      // Build connection shape
      return {
        edges: orders.map(order => ({
          cursor: encodeCursor(order.id),
          node: order
        })),
        pageInfo: {
          hasNextPage: orders.length === first,
          hasPreviousPage: !!after,
          startCursor: orders[0] ? encodeCursor(orders[0].id) : null,
          endCursor: orders.at(-1) ? encodeCursor(orders.at(-1).id) : null,
        }
      };
    }
  }
};

N+1 Problem in GraphQL Pagination

A critical issue: if each edge.node triggers a separate DB query, paginating 20 items causes 21 queries. Use DataLoader to batch these into a single query:

import DataLoader from 'dataloader';

const orderLoader = new DataLoader(async (ids) => {
  const orders = await db.orders.findMany({
    where: { id: { in: ids } }
  });
  return ids.map(id => orders.find(o => o.id === id));
});

WebSockets & Real-Time Pagination

Real-time pagination combines the concept of paginated history with live updates arriving via a persistent connection. This is one of the most complex pagination scenarios.

The Core Challenge

A paginated list of historical records + live incoming records creates two separate data streams that must be reconciled without duplicates or gaps.

Architecture Pattern: Dual-Stream Model

// Client connects and establishes two streams:
// 1. Historical: REST/GraphQL cursor pagination for past data
// 2. Live: WebSocket subscription for new data

const socket = new WebSocket('wss://api.example.com/stream');
let liveBuffer = [];
let syncPoint = null;  // Timestamp when WS connected

socket.onopen = () => {
  syncPoint = Date.now();
  // Subscribe to new events BEFORE loading history
  // to avoid the gap between last history item and first live item
  socket.send(JSON.stringify({ type: 'subscribe', since: syncPoint }));
  loadHistory();  // fetch pages until we reach syncPoint
};

socket.onmessage = (event) => {
  const msg = JSON.parse(event.data);
  if (historyLoadComplete) {
    displayLive(msg);
  } else {
    liveBuffer.push(msg);  // Buffer until history catches up
  }
};

async function loadHistory() {
  let cursor = null;
  while (true) {
    const page = await fetchPage(cursor);
    display(page.data);
    if (!page.hasMore || page.data.at(-1).timestamp < syncPoint) break;
    cursor = page.nextCursor;
  }
  // Flush buffered live events, deduplicate
  const deduplicated = dedup([...displayedItems, ...liveBuffer]);
  display(deduplicated);
  historyLoadComplete = true;
}

Server-Sent Events (SSE) for Simpler Real-Time

SSE is a one-directional HTTP streaming protocol — simpler than WebSockets for append-only feeds. The client uses a Last-Event-ID header for reconnection, which acts as a cursor:

// Server (Node.js/Express)
app.get('/api/feed/live', (req, res) => {
  res.setHeader('Content-Type', 'text/event-stream');
  res.setHeader('Cache-Control', 'no-cache');
  res.setHeader('Connection', 'keep-alive');

  const lastEventId = req.headers['last-event-id'];  // Auto-cursor!

  // Send missed events since last disconnect
  const missed = getMissedEvents(lastEventId);
  missed.forEach(event => {
    res.write(`id: ${event.id}\ndata: ${JSON.stringify(event)}\n\n`);
  });

  // Subscribe to new events
  const unsubscribe = eventBus.subscribe((event) => {
    res.write(`id: ${event.id}\ndata: ${JSON.stringify(event)}\n\n`);
  });

  req.on('close', unsubscribe);
});

// Client
const sse = new EventSource('/api/feed/live');
sse.onmessage = (e) => console.log(JSON.parse(e.data));
// Browser automatically sends Last-Event-ID on reconnect

  "type": "live_event",
  "data": { "id": 9999, "event": "new_order" },
  "event_id": "9999"
}

Handling Reconnections

On reconnect, the client must send the last event ID it received. The server replays any missed events from that point. This requires an event log or message queue (Kafka, Redis Streams) on the server that retains events for at least the expected reconnect window.

Section 11

High-Level / Distributed Systems Design

Pagination Across Microservices

When data lives in multiple services, pagination becomes a distributed problem. A common scenario: a "feed" API that aggregates posts from a Posts service, Ads service, and Recommendations service, all with different underlying data stores.

Approach 1: Fan-Out and Merge

// API Gateway fans out to N services, merges, sorts, slices
async function getFeedPage(userId, cursor, limit) {
  const [posts, ads, recs] = await Promise.all([
    postsService.getPage(userId, cursor?.posts, limit * 2),
    adsService.getPage(userId, cursor?.ads, 5),
    recsService.getPage(userId, cursor?.recs, limit),
  ]);

  // Merge and sort by timestamp
  const merged = [...posts, ...ads, ...recs]
    .sort((a, b) => b.timestamp - a.timestamp)
    .slice(0, limit);

  // Next cursor encodes state for each service separately
  return {
    data: merged,
    next_cursor: encodeCursor({
      posts: merged.filter(x => x.type === 'post').at(-1)?.cursor,
      ads: merged.filter(x => x.type === 'ad').at(-1)?.cursor,
      recs: merged.filter(x => x.type === 'rec').at(-1)?.cursor,
    })
  };
}

Approach 2: Pre-Computed Feed (Write-Time Fanout)

Instead of reading from multiple services at query time, pre-compute each user's feed into a dedicated feed table (write fanout). This is how Twitter (pre-2022) worked. Pagination then operates on a single, simple sorted list per user. Trade-off: expensive writes for users with millions of followers (celebrity problem).

Approach 3: Materialized View / Search Index

Aggregate data into Elasticsearch or a dedicated read model. The read model supports full-text search, complex filters, and efficient pagination. Updated asynchronously via CDC (Change Data Capture) from the source DBs using Debezium + Kafka.

Distributed Cursor Challenges

Clock skew: In distributed systems, clocks across nodes are not perfectly synchronised. A timestamp-based cursor from one node may not accurately represent ordering on another node. Solutions: use logical clocks (Lamport timestamps, Hybrid Logical Clocks), rely on monotonic sequence IDs rather than wall-clock time, or route all writes for a user/partition through a single primary.

Hot partitions: If many users paginate the same popular entity (e.g., a trending hashtag), the DB partition holding that entity becomes a hot spot. Solutions: read replicas, caching, or pre-pagination (pre-compute pages and cache them).

API Gateway / BFF Layer

The Backend-for-Frontend (BFF) pattern centralises pagination logic. Each client type (mobile, web, partner API) gets a BFF that implements the appropriate pagination strategy for that client's needs — mobile might use cursor pagination for infinite scroll, while the web app uses offset pagination for a traditional paginated table.

Pagination in Event-Driven Systems

Kafka consumer groups paginate implicitly via offsets. The consumer "cursor" is the Kafka partition offset. Key concepts:

  • Committed offset: Last successfully processed message per partition
  • Auto-commit vs manual commit: Manual commit gives at-least-once with idempotent processing
  • Consumer lag: Difference between latest offset and committed offset — the "backlog"
  • Replay: Reset offset to earliest for full reprocessing — equivalent to "go to page 1"

Caching Strategies

What to Cache

Cache-Friendly
  • Early pages (page 1 is fetched most)
  • Static or slow-changing data
  • Identical queries from many users
  • Total count (expensive, rarely changes)
Cache-Hostile
  • Personalised feeds (different per user)
  • High-write datasets
  • Deep pages (rarely accessed)
  • Real-time data

Cache Key Design

// For offset pagination
const cacheKey = `orders:list:page:${page}:size:${pageSize}:sort:${sortField}:${sortDir}`;

// For cursor pagination (hash the cursor)
const cacheKey = `orders:cursor:${sha256(cursor)}:limit:${limit}`;

// For filtered queries, include filter hash
const filterHash = sha256(JSON.stringify(sortedFilters));
const cacheKey = `orders:filter:${filterHash}:page:${page}`;

Cache Invalidation

This is the hardest problem. Strategies:

  • TTL-based expiry: Pages expire after N seconds. Simple but may serve stale data. Appropriate for data that can tolerate eventual consistency.
  • Write-through: On every write, invalidate all page caches for affected entities. Simple but blows cache hit rates if writes are frequent.
  • Tag-based invalidation: Tag cache entries (e.g., "orders:user:123"). Invalidate all entries with a tag on write. Redis supports this via sets of cache keys per tag.
  • Version tokens: Append a version/etag to cache keys. Increment the version on write. Old cache entries become inaccessible. Stale entries expire naturally by TTL.

CDN Pagination Caching

Public paginated APIs (e.g., public product listings) can be cached at the CDN layer. Use Cache-Control: public, max-age=60, stale-while-revalidate=300 headers. Cursor-based APIs have poorer CDN cache hit rates because each cursor is unique. Page-number APIs cache better — page 1 is always the same URL.

Redis Pipeline for Paginated Data

// Fetch page data + total count in a single round-trip
const pipeline = redis.pipeline();
pipeline.get(`page:${cacheKey}`);
pipeline.get(`count:${countCacheKey}`);
const [pageResult, countResult] = await pipeline.exec();

if (pageResult && countResult) {
  return { data: JSON.parse(pageResult), total: parseInt(countResult) };
}
// Cache miss: fetch from DB, cache results

Virtual Scrolling (Windowed Rendering)

Renders only the visible rows plus a small buffer. The DOM contains ~50 rows regardless of dataset size. A scroll event triggers offset recalculation and new pages are fetched as needed. Libraries: react-window, react-virtual, ag-grid.

// Simplified virtual scroll logic
const ITEM_HEIGHT = 50; // px per row
const VISIBLE_COUNT = Math.ceil(containerHeight / ITEM_HEIGHT);
const BUFFER = 5; // extra rows above and below

function getVisibleRange(scrollTop) {
  const startIndex = Math.max(0, Math.floor(scrollTop / ITEM_HEIGHT) - BUFFER);
  const endIndex = startIndex + VISIBLE_COUNT + BUFFER * 2;
  return { startIndex, endIndex };
}

// Determine which DB page to fetch based on visible range
const pageForIndex = (index) => Math.floor(index / PAGE_SIZE);
const pagesToFetch = [...new Set([
  pageForIndex(startIndex),
  pageForIndex(endIndex)
])];

Infinite Scroll Implementation

import { useInView } from 'react-intersection-observer';

function InfiniteList() {
  const { ref, inView } = useInView({ threshold: 0.1 });
  const [items, setItems] = useState([]);
  const [cursor, setCursor] = useState(null);
  const [hasMore, setHasMore] = useState(true);

  useEffect(() => {
    if (inView && hasMore) {
      loadNextPage();
    }
  }, [inView]);

  async function loadNextPage() {
    const data = await fetch(`/api/items?cursor=${cursor || ''}&limit=20`).then(r => r.json());
    setItems(prev => [...prev, ...data.items]);
    setCursor(data.next_cursor);
    setHasMore(data.has_more);
  }

  return (
    <div>
      {items.map(item => <Item key={item.id} {...item} />)}
      {hasMore && <div ref={ref}>Loading...</div>}  {/* sentinel */}
    </div>
  );
}

Preserving Scroll Position

Infinite scroll breaks the browser back button — returning from a detail page resets scroll position. Solutions: store scroll position in sessionStorage, use React Router's ScrollRestoration, or use URL state to encode the current "page/cursor" so the list can be reconstructed on navigation back.

UX Best Practices

  • Always show a loading indicator during page fetch (skeleton loaders, not spinners)
  • Show an error state with retry on network failure
  • Show "end of results" clearly for infinite scroll
  • For large tables, show the current range: "Showing 41–60 of 1,847"
  • Debounce rapid page changes / scroll events
  • Prefetch the next page before user reaches the end

Elasticsearch Deep Pagination Limit
By default, Elasticsearch limits from + size to 10,000 (configurable via index.max_result_window). Beyond this, you must use search_after. This is because deep offset pagination requires sorting and discarding enormous result sets across all shards.

search_after (Cursor Equivalent)

GET /orders/_search
{
  "size": 20,
  "query": { "match_all": {} },
  "sort": [
    { "created_at": "desc" },
    { "_id": "desc" }  // tiebreaker — _id is always unique
  ],
  "search_after": ["2024-01-15T10:30:00Z", "4892"]
  // Values from sort fields of last result
}

Point-in-Time (PIT) for Consistent Pagination

Without PIT, index changes between requests can cause search_after to miss or duplicate documents. PIT creates a frozen view of the index:

// Step 1: Open a PIT
POST /orders/_pit?keep_alive=1m
// → { "id": "46ToAwMDaWdVAWN..." }

// Step 2: Use PIT in search
GET /_search
{
  "size": 20,
  "query": { "match_all": {} },
  "pit": { "id": "46ToAwMDaWdVAWN...", "keep_alive": "1m" },
  "sort": [{ "created_at": "desc" }, { "_id": "desc" }],
  "search_after": ["2024-01-15T10:30:00Z", "4892"]
}

// Step 3: Close PIT when done
DELETE /_pit
{ "id": "46ToAwMDaWdVAWN..." }

Scroll API (Legacy — for full export)

The Scroll API holds a search context open and iterates all results. It's designed for full dataset export, not interactive pagination. Deprecated for new use cases in favour of PIT + search_after. Still useful for ETL/migration.

Decision Framework

How to Choose in an Exam (or Interview)
1. Does the user need to jump to arbitrary pages? → Offset (accept perf trade-off) or hybrid.
2. Is the dataset large (>100k rows) and growing? → Cursor/keyset.
3. Is the data time-series or event-based? → Time-based + Snowflake/ULID IDs.
4. Is consistency critical (no duplicates ever)? → Snapshot transaction or PIT.
5. Is it a real-time feed? → Cursor for history + SSE/WebSocket for live.
6. Is it full-text search? → Elasticsearch search_after + PIT.
7. Is it a leaderboard? → Redis ZSET.
8. Is it a browser list with 10,000+ items? → Virtual scrolling.
Section 16

Common Exam Questions & Model Answers

Q: Why is OFFSET pagination slow for large datasets?

A: The database must read and discard all rows before the offset. For OFFSET 1000000 LIMIT 20, the DB scans 1,000,020 rows and throws away the first million. This is O(n) in the offset value. Cursor pagination replaces the OFFSET with a WHERE clause that the DB can satisfy with an index seek in O(log N), then scans exactly LIMIT rows.

Q: What's the "phantom read" problem in pagination?

A: When data is mutated between page fetches. With offset pagination, if a new record is inserted into an earlier position, every existing record shifts down by one position. A client viewing page 2 will see the last record from page 1 again — a duplicate. If a record is deleted, a record will be silently skipped. Cursor pagination avoids this by anchoring on record identity (key value), not position.

Q: Design a scalable pagination system for a social media feed with 100M users.

A: Use a write-time fan-out architecture. When a user posts, write to the feed tables of all their followers asynchronously (via a message queue). Each user's feed is a sorted set in Redis (ZADD feed:user_id timestamp post_id). Paginate using ZREVRANGEBYSCORE with time-based cursors. For celebrities (many followers), use read-time fan-in instead (pull from their timeline at read time and merge). Cold storage (older items) uses cursor pagination against a Cassandra or PostgreSQL table. Live updates use SSE or WebSocket.

Q: How would you implement pagination for a search results API?

A: Use Elasticsearch. For interactive search (first 10,000 results), use from + size. For deep pagination or full export, open a Point-in-Time, use search_after with the sort values from the last hit as the cursor, and close the PIT when done. Always include a unique tiebreaker (_id) in the sort clause. Approximate total count from Elasticsearch's hits.total.value.

Q: How does GraphQL Relay cursor pagination work? Why use edges/nodes?

A: The Relay spec wraps results in a Connection type. Each item is an Edge containing a cursor (opaque string for that specific position) and a node (the actual data). The Connection also has a pageInfo object with hasNextPage, hasPreviousPage, startCursor, endCursor. The edge/node indirection allows per-item cursors (useful for live update subscriptions) and connection-level metadata (totalCount). Cursors are typically Base64-encoded position identifiers, not tied to pagination mechanism — the backend can use keyset, offset, or anything internally.

Q: How do you paginate across microservices?

A: Two approaches. (1) Fan-out and merge: the aggregating service requests LIMIT * N items from each upstream, merges and re-sorts, then returns LIMIT items with a composite cursor that encodes per-service cursor state. (2) Pre-aggregated read model: a separate service or materialised view aggregates all data (via CDC/Kafka) into a single sorted store (Redis, Elasticsearch, or a dedicated DB). Pagination then runs against the aggregated store. Option 2 has better read performance but higher write cost and latency.

Q: How do you handle real-time updates in a paginated list?

A: Subscribe to updates via WebSocket or SSE before loading history. Record the connection timestamp as the sync point. Load historical pages (via cursor pagination) until reaching the sync point. Buffer live events received during history load. Once history is complete, flush the buffer, deduplicating any overlap. Going forward, append live events to the top of the list without re-fetching pages. For pull-to-refresh, use a since=timestamp query to get only new items.

Q: What is a covering index and why does it matter for pagination?

A: A covering index includes all columns needed by a query (SELECT, WHERE, ORDER BY) so the DB can satisfy the query entirely from the index without accessing the table heap. For pagination, this eliminates the "late row lookup" problem — the index-only scan reads exactly LIMIT entries sequentially after the seek, with no random heap I/O. This can be 10x+ faster on large tables. In PostgreSQL, use the INCLUDE clause to add non-key columns to an index. In MySQL, the index must explicitly contain all needed columns.

Q: What are the consistency trade-offs of different pagination strategies?

A: Offset pagination has the worst consistency — any insert or delete shifts positions and causes duplicate or missing items across pages. Cursor/keyset pagination is immune to inserts between pages (cursor anchors on a specific key value) but vulnerable to deletes — if the cursor row is deleted, behaviour depends on implementation. Snapshot/REPEATABLE READ offers perfect consistency — the entire dataset is frozen at the time of the first query — but holds a database snapshot open, preventing cleanup, and is expensive for long-running paginations. Elasticsearch PIT offers index-level snapshots without DB transaction locks.
